发现不少小伙伴很好奇我是怎么用 Mac 来开发 Windows 软件的，以及 Windows 软件现在一般用什么技术栈来实现，刚好有空，来和大伙随便聊聊关于多客户端下技术选择的思考以及我的一些想法。前几天在推上连着发了三篇，这里整理成一篇放到博客里。

## 端的开发一般是这三条路

做过前端客户端的小伙伴应该都知道，这些年端的开发一般是这三条路。

第一种最简单方便的是，直接写 Web 代码，塞到浏览器就能跑，包括早年的 PhoneGap、Cordova 就是把网页塞进一个原生壳里，然后提供一些 bridge 的能力让 JS 可以调用到一些原生的能力，比如唤起手机摄像头这类的 Web 不好做的事情。

第二种是跨端开发，也就是好多年前大家经常听到的一码多端，当时移动端有 React Native、Weex 这一类技术，当时主要是为了解决 Web 性能差的问题，一份代码同时打包出 iOS 和 Android，这里国内大厂使用跨端技术还有一个非常大的原因就是动态化和热更新，讲的土一点就是可以绕过商店审核直接下发新页面，这也是国内跨端在当时移动互联网高速发展时特别流行的重要原因。

桌面端大家熟悉的就是 Electron，大家熟知的现在不少 AI 桌面端、VS Code、Slack 是用这个做的，代价是相当于每个应用都自带一份 Chromium 和 Node.js，安装包一百多 MB，内存也占得多。但好处是在 Chromium 渲染引擎的统一下能够很好地保持多端的展示一致性，加上里面写的代码非常好写，后续不少桌面的速成就会用这个技术。

跨端后面也慢慢延伸出更多有趣的解决方案，类似 Flutter 自己实现一套渲染引擎，早期靠 Skia，现在换成了自研的 Impeller 渲染引擎来保障多端一致和性能效率的均衡，包括桌面端上老牌的 Qt，和 Flutter 一样自己画界面。

这两年桌面跨端也出现了用 Rust 写的 Tauri、Go 写的 Wails，它们和 Electron 不一样的地方就是，没有塞一个 Chromium 进去，而是使用的系统自带的 WebView，包会小非常多，但是整体还是基于 Web 这一套研发思路和对应实现语言去进行桥接交互，但是由于系统 WebView 每个平台不一样，Windows 上是 WebView2，Mac 上是 WKWebView，Linux 上是 WebKitGTK，所以多端显示的一致性反而不如 Electron，还是要写兼容代码。所以这种情况下，即使 Electron 很大内存占用也不低，还是会被选择更多。

第三种是原生开发，也是没有 AI 之前，大家觉得开发难度很大的一种方式，特别是之前的苹果系使用的 Objective-C，Android 系使用的 Java、Windows 系 C++、C#，均是我认为需要科班花非常多时间去学习、看书、手编代码，要想做得好，需要花大量时间研究对应的系统底层原理，能够方便你写出相比普通研发性能更好更稳定的代码，在我看来是前期投入大，后期用户很享受的技术。我 17 年那会儿刚工作不久，职业发展比较爽的一个很大原因，是抽了半年时间学习 Objective-C 和 iOS 研发，让本职是前端的工作提前往跨端方向走了，刚好可以解决一些只懂前端或只懂客户端都搞不定的难题，那也是我做一线开发非常快乐有趣的一段时间。

等到后面 Swift + SwiftUI、Kotlin + Jetpack Compose、C# + WinUI 3 慢慢出来成熟后，这些原生端语言的写法也慢慢向前端的声明式写法靠齐，也更易写了，声明式代码更短、更好读了。但是在国内，原生完全被 React Native、Flutter、Electron 的广泛使用盖过去了，开发者不多，生态发展完全靠官方推动，这也是为什么很多 App 出活很快，但大家普遍觉得用久了卡卡的，而且这类 App 还占了大头。想迁移到原生的话，假如之前架构实现得不好，大概率只能重写，完全不能复用，实现得好，比如你早就把业务逻辑抽出来了，类似 Kotlin Multiplatform 这类方案把业务逻辑共享、界面各写各的原生，算是第四条路，也是最近几年的趋势。

聊到这里大家应该大概明白了，这里也有一个不可能三角，就是研发效率、体验、性能这三者，选择 Web 是多效率少性能，选原生是多性能体验少效率，选跨端就是刚好是这三者取一个中间，做得好容易都占，做得不好，容易没有一边占到好处的尴尬局面。

![研发效率、体验、性能的不可能三角，Web 靠近效率，原生靠近体验和性能，跨端取中间](https://cdn.tw93.fun/blog/pic/client-tech-triangle.svg)

那么在 AI Coding 写代码已经不是问题的情况下，我们应该选择啥技术呢？很多时候也取决于你的场景，比如你就是一个 Web 场景的浏览、点点按钮、阅读这一类 Web1.0 阶段的东西，那还是非常建议直接 Web 技术来弄；假如你需要调用到系统底层的能力，或者需要操作更顺手更好分发，以及本身就是一个应用的场景，我还是非常建议使用原生技术来实现，这样可以第一时间享受到系统官方本身的众多调优，以及最原生的交互效果、最低的内存占用，加上 AI 让写两份原生代码的成本大幅下降，三角形的效率那一边被补上了，只是两个平台的调试和验证变成了新的成本，这里正是人需要重点做的事情了。

当然假如实在技术选型不那么重要，工作量非常之大，以及业务效果远大于技术体验选择，选择跨端技术也是可以的，这样快，迭代发布也快，可以第一时间让你的用户收到你的最新的特性更新。

## Windows 上也想着不将就

技术栈上，Mac 版本的 Mole 使用的也是原生的 Swift + SwiftUI，能够让我很好调用系统能力以及非常好的性能体验，想着不将就，所以在 Windows 上我也是想着直接用本身写 Windows 软件最直接的语言，C# 加 WinUI 3，跑在 .NET 10 上，过程虽然难搞，但是相比十年前我了解轮子哥谈的 Windows 开发要简单好理解一些了。

Windows 上的原生界面框架其实挺多的，包括很多年前了解过的 Win32、WinForms、WPF、UWP 这一波，WPF 是 2006 年出的，到现在还在维护，但控件和设计语言不是很好看，非常上一代的感觉，然后 UWP 又被沙盒和应用商店给绑定住，现在微软主推的是 Windows App SDK 里的 WinUI 3，界面框架从系统里面拆出来单独发版，这样就有一个好处，普通的 Win32 程序也能用，基础组件就是 Windows 11 自己的 Fluent 风格，我还挺喜欢，高分屏缩放和 ARM64 都是原生支持。

然后这里 .NET 10 是去年 11 月发的长期支持版本，打包时我把运行时一起打进去，用户不需要另外装 .NET，x64 和 ARM64 这里各出了一个原生安装包，骁龙的 Windows 笔记本就不要走转译了，相当于尽量让用户使用简单不折腾。这里安装和更新用的是开源的 Velopack 框架，可以很方便做增量更新，也很好用。

工程师开始写代码时候肯定会想到能复用尽量复用，所以我开始写的时候也非常想复用 Mac 的 Swift 代码，后面让 AI 分析了一下，十几万行 Swift 代码可以脱离 AppKit、SwiftUI 这些系统框架使用的 20% 都没有，处理的逻辑也是 `~/Library` 这类 macOS 自己的路径规则，基本用不上，所以 Windows 版几乎是从零开始写的。

## 能复用的是设计、文案和规则

两边的关系其实非常简单，外观和交互我尽量完全一致，尽可能让大家意识里面认为的 Windows 软件不那么精致美观的感觉在这里也保持我认为好的水平，然后底层代码各写各的，关于视觉的一致性还原有了 AI 以后很简单，我把原本的 Mac 版写在 Swift 里的颜色、字号、间距、圆角这些设计 token，直接写了一个脚本生成为 Windows 里面 XAML 资源，文案也是从 Mac 的多语言文件转成 Windows 的格式，11 种语言一起转过来，甚至大家看到的菜单栏里面的那个 runner 动画也是用的同一个脚本同步来的。

![左边是 Mole Mac 版的清理页，右边是 Windows 版，颜色、字号、间距和文案都由同一份设计 token 和多语言文件生成](https://cdn.tw93.fun/blog/pic/client-tech-mole-mac-windows-clean.webp)

虽说同步，可能大家会觉得很简单，其实这里需要花点精力防止 AI 直接给你跑偏了，每次同步其实我会记录对应的是 Mac 的哪一个提交，这样两边就不会走偏去，然后功能上会有一份 SYNC.md 当做对账表，Mac 每加一个功能、修一个安全问题，Windows 这边都会标清楚哪些是已经实现、哪些是刻意不同还是不适用，以及为什么这样判断。

通过这两个机制，我可以很好的让两边的底层完全各写各的，但是又能很好地保持功能对齐，完全不需要刻意去硬写一层兼容去磨平，反而会变复杂，这里能复用的反而是设计、文案以及踩坑后定下来的各种规则，反而这些是 AI 非常喜欢的“能力抽象层”，也就是说随着时代发展，慢慢所谓的代码抽象没有那么重要了，反而是规则抽象更重要。

## 签名比 Mac 麻烦不少

另外 Windows 开发还有一块比 Mac 要麻烦不少，就是证书签名，没有签名的，一打开会出现「Windows 已保护你的电脑」，甚至 Windows 11 的智能应用控制会直接不让运行，国内不少安全软件也会把没签名的程序当成可疑报毒，这和 Mac 上没签名、没公证的软件提示「已损坏」差不多，平时 Mac 上大家还可以跑一条命令解掉，Windows 上想正规分发，这一步没有啥好办法，就是需要。

调研下来微软的签名生态的确比苹果差太多了，微软有自己的 Azure Artifact Signing，一个月 9.99 美元最省事，居然个人只开放给美国和加拿大的开发者，没办法使用，很奇葩的规定，然后行业还规定从 2023 年起签名私钥必须放在硬件或者云端 HSM 里，不能再是电脑上的一个文件，今年起单张证书最长只能用 460 天，差不多一年多就得换一次证书。

最后我买的是 Certum 的云端 OV 证书，3 年 3 百多美元，签名时登录电脑上的 SimplySign，再用手机上的 App 给一个动态码，SmartScreen 的信誉也跟着证书上审核过的名字慢慢积累。刚开始一段时间的签名包在 ThinkPad 上也会一样被 SmartScreen 拦了下来，后来我每次发版都把安装包提交到微软的恶意软件分析门户，让信誉慢慢积累起来，而且 SimplySign 的登录会话闲置几个小时就会断开，需要再次输入动态码才能继续签名，所以这里其实很难做成云端自动打包。

## 所有事情还是在 Mac 上做

证书搞定后，就是开发环境的事情了，我的研发要求是代码和 AI 的上下文必须全留在 Mac 上，Mac 用习惯了，真的很难使用 Windows 去研发，这里 Windows 只负责编译和验证效果和各种测试，所以我在 Mac 上装了 Parallels Desktop，大概 3 百多块一年，之前也听不少小伙伴吐槽过这个软件，不过在我的 M5 Pro 上跑 Windows 11 还挺顺滑，让我感觉这个钱花得很值。

它最好用的一点是我的 Claude 能很顺手地操作它，仓库直接作为 Parallels 的共享文件夹挂进虚拟机，变成一个 X 盘，Mac 上改完代码，虚拟机里直接编译，不需要来回 Copy 文件，只是两边的编译产物要分到不同的目录，对于编译、启动、看日志的工作都被我写成了脚本，通过 Parallels 自带的 prlctl exec 直接在虚拟机里执行，程序启动就崩的时候 Windows 只给一个 0xc000027b，Mole 会把真正的异常写进日志，脚本跑完顺手打印出来，Claude 直接就能读到。相当于写代码还是在 Mac 上的 Claude Code 里，调试和运行都在虚拟机里，脚本不能解决的地方，直接用 Codex 的 computer use 去点，只有少部分那种系统确定弹框点不了，我在这里就是这个职责，点点系统弹框确定，哈哈。

![代码和 Claude Code 都在 Mac 上，大部分编译和测试在 Parallels 虚拟机里跑，虚拟机测不准的放到 ThinkPad 真机上验](https://cdn.tw93.fun/blog/pic/client-tech-devloop.svg)

说到这里，可以和大伙分享一下 Mole Windows 的架构分层，一共四层，最底下的 Core 只依赖 .NET，不碰任何 Windows 接口，清理规则、路径安全检查、卸载残留的判断都放到这里，测试用的是一个按 Windows 路径规则模拟出来的内存文件系统，这样在 Mac 上也可以很好的跑；往上是 Platform 层，注册表、文件系统、Win32 调用这些真正的系统接口都放在这一层，打开 EnableWindowsTargeting 以后，Mac 上也能编译通过；再往上就是写过应用同学非常熟悉的界面状态的 ViewModel 层，这里和 Mac 版本会一一对应，这样也能够在 Mac 上测，只有最上面这一层的 WinUI 界面必须去 Windows 里编译。

![Mole Windows 的四层结构，越往下越不碰 Windows，越多代码可以在 Mac 上验证](https://cdn.tw93.fun/blog/pic/client-tech-layers.svg)

这也是让我一个月时间可以写 8 万多行 Windows 代码、4000 多个测试，但是几乎大部分可以在 Mac 上完成的一个很方便的地方，也是架构设计的巧妙处，当然这里我只提供之前做架构时候的想法建议，大部分是 Opus 5.5 去帮我整的，很牛逼。

接着可以聊测试了，我反而认为在 AI 时代，工程师最大的价值，除了架构设计外就是这个测试验证了，所以为了保证产品是可以售卖的，肯定需要在真实环境测试验证，反复找体验问题去修复的，所以我整了一台 ThinkPad X1 Carbon，这个机器质感还不错的，我把它当成真机环境，设置永不休眠，可以让我和我的 Agent 24 小时去验证测试回归，包括获取各种真实系统环境的参数验证，400 多款 Windows 软件的卸载、残留清理、注册表、启动项测试，大部分在虚拟机里跑，x64 安装包、真实的高分屏、电池、SmartScreen 这些虚拟机看得不准确的，就直接放到这台机器上验，所以这台机器让我感觉也非常值。

然后为了不想在两台机器拷来拷去，最后还是用了 UU 远程，直接在 ThinkPad 那边开一个远程终端，我这边在 Mac 上直接操作，然后还把 ssh 连接当做备用，大部分软件的安装、卸载和调试，都是通过命令行脚本去完成的，剩下需要看界面的，直接通过远程桌面让 computer use 去操作，非常方便，最终相当于我还是在 Mac 上做的所有的事情。

![我的工作台，中间是 Mac，左边是 ThinkPad X1](https://cdn.tw93.fun/blog/pic/mole-product-workspace.webp)

这个过程下来，到最后成品让几个 Mole 天使用户去试用，大伙用着很爽，感觉这个过程的开发非常值，很有意思，而且可以帮助大家解决不少痛点，加上 Windows 上小白用户应该比 Mac 要多不少，让他们也享受到好软件的体验其实很值得开心。

## 借其他语言的生态补短板

技术栈选好以后，再来聊聊我们在进行客户端应用研发的时候，如何利用各种技术语言的特性来帮助我们产品做得更好。

比如说写 Mac 应用你的主语言是 Swift，其实你完全可以融入一些其他的语言来帮助你解决这个语言不那么擅长的某些地方的问题，当时 6 年前做[妙言](https://miaoyan.app)的时候就是这样，这是一个原生的 Mac Markdown 笔记应用，使用纯 Swift 实现，当时有一个非常难解决的问题卡住我，就是如何用 Swift 来实现一个 Markdown 的格式化能力，很像我们在 VS Code 里面使用 Prettier 的 Markdown 格式化那个能力的效果。

当时想用 Swift 手写实现这个能力，原本的就是用 JS 实现的，非常复杂差不多快要放弃了，洗澡的时候突然想到一个点子，其实在 Swift 里面我完全可以去调用一个 JavaScriptCore 的能力，它是可以执行 JS 的，那我是不是可以把杂乱的 md 当做一个字符串传到这个里面去运行，然后帮我输出非常清晰规范化的 md 字符串，我再解析渲染出来，立马去测试验证，真的可以，效果感觉非常不错，在当时没有 AI 的时代，假如我用 Swift 去实现这个格式化引擎，不知道要多久才搞得出。

再到后面，就更有意思了，当时写 [Pake](https://github.com/tw93/Pake) 这个桌面打包工具的时候，主要是 Rust 写的，但是 Rust 的生态在当时也非常差，比如我想写一些下载的能力，完成后弹出一个 Toast 的能力，它甚至都没有成型的 Toast 组件，既然我会前端，当时想到的点是，可以通过 Rust 去调用 JS，让 JS 生成一个 document 容器塞到 Web 里面去，这样在有消息通知的时候，我可以让 Rust 去调 JS，把这个东西渲染出来，效果也非常好，同时不会影响原有的性能，还能够更美观。

![用 Pake 把微信读书打包成的桌面应用](https://cdn.tw93.fun/blog/pic/client-tech-pake-weread.webp)

其实很多时候，假如你对各种语言都了解一点，碰到难搞问题的时候可以帮助你很快想到一些 Hack 的办法去解决，甚至你还会融会贯通，反过来调用，比如当时在渲染的 Web 里面，需要去调用下载的能力，这个时候还可以反向去调用 Rust 的成型的系统能力帮我去下载，性能就更高。

这个里面有一个很有意思的技术，讲土一点，你可以把它理解成通信，相当于不同语言之间可以通过一个中间层去交换信息，然后监听各自执行，刚刚上面 Rust 和 JS 相互调用这里就使用了这种技巧，开头说的 PhoneGap 给 JS 开的 bridge 也是这种通信。甚至当你脑洞大开的时候，你甚至可以多个语言相互通信，当时做妙言的分栏编辑功能时候，一边是原生的 Markdown 编辑器，一边是 WebView 渲染的预览效果，Markdown 解析用的是 GitHub 开源的 C 语言库 cmark-gfm，性能和能力都非常牛逼，但是很底层，它可以在每一块 HTML 上标出对应原文的第几行，然后我用预览里的 JS 读这些标记，算出当前滚到了第几行，再通过消息通道告诉 Swift，编辑区同步跟着到这个位置，这样就很好实现了两边滚动预览效果是非常同步的。

![妙言的分栏编辑，左边是原生编辑区，右边是 WebView 渲染的预览](https://cdn.tw93.fun/blog/pic/client-tech-miaoyan-split.webp)

当时 [Kaku](https://kaku.fun) 里面也有用过类似的能力，有一个功能是你直接在终端里面输入 # 加一句自然语言回车，我可以帮你去调用一个快速的 AI 帮你生成一个终端可执行命令，这个效果非常酷。

![Kaku 里输入 ## 加一句话，会给出几条命令让你挑，输入 # 则直接填好一条](https://cdn.tw93.fun/blog/pic/client-tech-kaku-commands.webp)

但是实现起来其实也很难，因为正常时候你直接回车，你的 zsh 就报错了，不会执行这一块，因为它不认识，当时也想了很久，发现我可以用终端的转义序列把这句话发给 Kaku，里面的 Lua 脚本接到后交给 Rust 这一层去请求模型，生成的命令再用 Lua 回填到命令行，有一种偷梁换柱的感觉，等一小会儿命令就填好了，然后他可以很自然的回车，这条自然语言生成的命令就执行了，相当于一句话在 zsh、Lua、Rust 走了一圈，最后回到终端上了。

![妙言的同步滚动走了 C、JS、Swift 三层，Kaku 的一句话在 zsh、Lua、Rust 之间走了一圈](https://cdn.tw93.fun/blog/pic/client-tech-relay.svg)

类似这样的场景还挺多的，这种难题的解决是在前 AI 时代，我认为作为工程师最有意思的地方，你可以完全把各种语言当做一个工具，没有任何偏见的去使用，只基于场景选择最合适它的语言，而非我喜欢这个语言，就用这个语言去实现所有的功能。

也即我们做产品的时候，需要充分去利用各个语言生态的特性，来弥补做客户端时候本身语言的一些短板，同时把原本的高性能、交互不错的优势发挥到最好，这样最终效果就非常互补，很有意思。

## 解决问题比选技术栈更重要

不过说到底，技术是给业务服务的，最终还是需要往解决问题方向走，好比抢演唱会门票，大家不会关注你这个客户端怎么这么卡，只会关注我用你能不能抢到票，即使你做得十分顺畅，但是抢不到票也是会被骂得很惨，技术栈的选择在这里选得好只是锦上添花，最终还是需要优先保障用户的最真实需求的解决，然后做好这里，再去想，我如何让用户体验更好，接下来才是考虑我是否需要使用原生技术来实现。

只不过到了现在的 AI 时代，原本很有意思的编码解决难题的场景变少了，直接上来一个 Opus 5.5 全部一把梭就帮你解决了，不过假如你了解这些各种语言的特性，你可以在它跑偏的时候，提醒一下它去试试那个语言的那个特性或者那个库，说不定可以帮助你做产品少走不少弯路。

哈哈，我现在就想着好好珍惜还能够在某些方面指导 AI 干活，说不定再过半年，这个活也不需要工程师干了，AI 可以完全帮你做了，那会更有趣还是更无趣呢？

我这种 AI 乐观派会认为编码这个事情应该就没意思了，不过还会有更多有趣未知的新东西值得我们去探索，那会更有意思些！
